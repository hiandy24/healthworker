# Playbook：架构与数据安全设计

审查对象不是单条调用，而是**设计决策是否被代码守住**：一致性边界有没有被新代码绕过、每条写路径的并发原语是否齐备、约束是否纵深到数据库层。本层缺陷多为 P0/P1（数据不一致、裁决点被绕过），但取证门槛也最高：并发行为的主张必须 L1（workerd/D1 真实并发复现）；静态推导只能 L2 且显式写"未运行"。

与其他 playbook 的分工：`playbook-contracts.md` 问"这条调用的协议对不对"（头、schema、错误码）；本文件问"**防线是否存在、是否完整、是否被绕过**"。

## A. 写路径并发原语矩阵（先填表，空格即候选发现）

对**每一个**服务端写路径逐条核对。基线（2026-09 时点，行号会漂移，以实际代码为准）：

| 写路径                       | 版本 CAS                      | 幂等                        | 原子性                                            | 裁决机制                                                |
| ---------------------------- | ----------------------------- | --------------------------- | ------------------------------------------------- | ------------------------------------------------------- |
| `POST /workouts`（仅 Agent） | 不适用（新建，version=1）     | `Idempotency-Key` 必须，24h | 单 `batch()`（幂等行+guard 行）                   | 唯一索引 `(principal,scope,key)` 兜底并发重放           |
| `PUT /workouts/{id}`         | `If-Match` 必须（缺 → 428）   | —                           | 单 `batch()` + guard 断言                         | `version=version+1 WHERE id AND version` + 触发器 ABORT |
| `DELETE /workouts/{id}`      | `If-Match` 必须               | —                           | 单条 CAS DELETE + 级联                            | `RETURNING` 判定 0 行即冲突                             |
| `POST /exercises`            | 不适用（新建）                | —                           | 待核对                                            | 语义 CHECK / 唯一性                                     |
| `PATCH /exercises/{id}`      | `If-Match` 必须 + 条件 UPDATE | —                           | 条件更新                                          | `exercise_referenced_semantics` 触发器保护被引用定义    |
| `PATCH /settings`            | `If-Match` 必须               | —                           | 单 `batch()`（首建 `WHERE version=1` + 条件更新） | 单例行 CAS                                              |

矩阵用法：**新增任何写路径（恢复导入、批量操作、管理脚本）必须先填进这张表**；填不出并发原语的路径就是 P0/P1 候选。已建路由则以当前代码重填，与基线的差值即发现项。

## B. 一致性边界与所有权

| 检查点         | 具体问法                                                                                                                | 取证方式                                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 不变量闭合     | 每条强不变量（计量互斥、位置唯一、completed 联动）是否完整落在一个聚合 + 一个事务内？有没有跨表不变量靠两次写维持？     | 列不变量清单 → 对应到 CHECK/触发器/batch 边界      |
| 单一写入者     | 同一张表是否只有一个写入入口？有没有脚本、导出回写、第二个路由写同一张表？                                              | grep 该表全部 INSERT/UPDATE/DELETE 语句，数入口    |
| 跨聚合引用     | 引用其他聚合的字段是否快照化（`exerciseNameSnapshot`/`measurementSnapshot`）？有没有新代码改回活引用（join 最新定义）？ | 检查读路径与统计是否只用快照列                     |
| 引用有效性窗口 | "仅对**新增**引用校验当前定义、历史引用豁免"的语义是否仍成立？                                                          | 归档动作 + 保留旧 entry 的 PUT：应成功且旧快照不变 |
| 删除语义方向   | `ON DELETE CASCADE`（聚合内）与 `RESTRICT`（被引用的定义）是否与所有权方向一致？新增外键有没有破坏方向？                | 内存库实验：删除被引用的定义 → 应 RESTRICT 失败    |

## C. TOCTOU 与事务原子性

先查后写（read→decide→write）是本层高发区。规则：**判断依据必须在写入事务内重新验证**，只做预查询判断 = 窗口（同 `playbook-contracts.md` §6.5，此处按设计层汇总）。

| 检查点           | 具体问法                                                                                                               | 取证方式                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 判定位置         | 每个"读出来再判断"的条件（版本、归档、存在性）是否写进事务内条件（`WHERE` / guard 断言 / 触发器）？                    | 逐条写路径画出"判断点 vs 写入点"，找时间窗口   |
| guard 覆盖完整性 | guard 条件是否覆盖全部外部依赖（`workouts.version`、`exercises.version+archived_at`）？新增依赖时 guard 有没有跟着加？ | 对照 saveWorkout 读取的外部状态与 guard 生成处 |
| 失败残留         | batch 失败后 `workout_write_guards`、`idempotency_keys` 是否可能留残行？（HW-2026-09-14-06 已涉及 WHERE 缺失）         | 制造 batch 中途失败（触发器 ABORT），再查两表  |
| 版本推进         | CAS 成功路径是否全部 `version=version+1`？有没有写数据却不推进版本的路径（等价于绕过乐观锁）？                         | grep 全部 UPDATE 语句核对 version 表达式       |

## D. 约束分层（防御纵深）

四层必须同向：应用层校验 → Zod schema → DB CHECK/唯一索引 → 触发器。数据库层是最终裁决者，应用绕不过去。

| 检查点   | 具体问法                                                                             | 取证方式                                 |
| -------- | ------------------------------------------------------------------------------------ | ---------------------------------------- |
| 库层兜底 | 应用层每条强校验在库层是否有对应约束？只存在于应用层的强不变量即缺陷（AGENTS.md §4） | 对拍"路由校验清单 vs schema.ts 约束清单" |
| 约束可达 | 直接写库验证约束真的拒绝坏数据，而不是只读 schema 定义                               | 内存库插入越界值，断言失败               |
| 参数化   | 新增 SQL 是否全部参数化绑定；`inserts()` 只接受固定表名                              | grep 字符串拼接 SQL                      |

## E. 交互与读侧一致性

| 检查点          | 具体问法                                                                                                       | 取证方式                      |
| --------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| 错误码=并发契约 | 412（版本前置失败）/ 409（状态冲突）/ 428（缺前置）是否被调用方区分处理？前端收到 412 是刷新重拉还是静默失败？ | 前端错误分支逐条对照          |
| ETag 闭环       | GET 的 ETag 是否原样用于下一轮 `If-Match`？重放响应的版本与存储是否一致？                                      | 复现一条 GET→PUT 链路         |
| 游标会话一致性  | 分页游标是否绑定 filter 快照并在筛选变化时失效？排序键是否稳定（三键 keyset）？                                | 并发插入 + 翻页，核对无漏无重 |
| 幂等重放语义    | 重放是否返回原始响应体并标注 `replayed` + 当前 `requestId`？（HW-2026-09-14-07）                               | 同 key 同 body 二次 POST      |

## F. 架构漂移（防线被绕过）

新增代码最常见的问题不是写错，而是**绕过既有裁决点**：

- **第二实现**：前端/Skill/文档各自重写一份统计、校验、单位换算（必须走 `src/shared` 与后端服务）。
- **第二入口**：绕过 Access/JWT 中间件的直接写路径；把生产 D1 绑定引入本地或自动测试。
- **第二契约**：新增字段只改后端与 UI，没同步 `src/shared`、OpenAPI、Skill 数据字典（契约漂移，AGENTS.md §5）。
- **静默扩权**：Agent 路由新增非只读能力；`workoutRoutes(agent)` 在 POST 后 `return` 的能力收口被破坏。

## 常见缺陷形态（架构层优先排查）

1. 新增写路径没填并发原语矩阵（无 CAS / 无幂等 / 拆成多个 batch）。
2. 读-判-写窗口：判断只在预查询，未进事务条件（TOCTOU）。
3. 跨聚合活引用回归：新功能 join 最新定义，历史统计口径漂移。
4. 强不变量只在应用层，直接写库可绕过。
5. 错误码语义合并使用，客户端无法区分"重取数据再试"与"放弃"。
6. 幂等记录与业务写入不在同一事务，出现"记了 key 没建数据"或反之。
7. 前端自行推导派生数据（统计、版本、单位），与后端口径分叉。

## 严重度映射

- 裁决点被绕过 / 数据不一致不可恢复 / 安全边界突破 → **P0**。
- 并发窗口内不变量被破坏但可检测或可恢复 / 历史口径漂移 → **P1**。
- 防线存在但取值或语义不当（错误码混用、约束过宽/过严）→ **P2/P3**。

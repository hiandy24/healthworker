# Playbook：健壮性、可维护性、测试覆盖空洞

这一层的产出多为 P2/P3，但很容易被"测试全绿"掩盖。每条都要给出**取证方式**，不要让结论停在"看起来不严谨"。

## A. 健壮性

| 检查点       | 具体问法                                                                                               | 取证方式                                               |
| ------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 异常捕获面   | 捕获元组是否漏了实际可能抛出的类型？损坏输入是否变成 traceback 而不是受控错误？                        | 构造畸形输入跑一次脚本/路由，观察 stderr 与退出码      |
| 宽泛判断     | `'status' in error && error.status === 400` 这类鸭子判断是否会误吞其他错误？                           | 追踪该分支能捕获的全部错误类型                         |
| 非空断言     | `x!`、`data[0]!`、`find(...)!` 在数据缺失时会不会变成 500                                              | 找到每个 `!`，问"什么情况下为 undefined"               |
| 分块与循环   | 分块大小是否可能为 0 或负数？`while` 是否保证推进？                                                    | 代入极值（键数 > 100、长度 0、长度 1）手算             |
| 数值与单位   | 整数/浮点换算、NaN/Infinity、-0、三位小数边界、上下限是否一致                                          | 单元级最小实验（node -e 或 sqlite3）                   |
| 上限成对     | UI 允许的规模 vs 服务端 body 上限 vs DB CHECK vs 导出上限是否互相矛盾                                  | 把三处常量列成表，找不可能同时满足的组合               |
| 并发与幂等   | CAS 是否在事务内判定？重放是否返回原始响应并标记？失败是否整体回滚、不留残留行？                       | 写并发复现（两个真实请求/两个客户端）                  |
| 清理与副作用 | 失败路径是否留下临时表行、临时文件、半写状态                                                           | 制造失败后查表/查文件系统                              |
| 时间与时区   | DST 缺口与重复、跨午夜、半开区间、1900/9999 边界、默认范围是否用 UTC 日历而归属用 localDate            | 直接跑共享日期函数的边界样本                           |
| 网络与重试   | 超时是"每次 socket 操作"还是"整体 deadline"？哪些错误必须不重试？退避与 Retry-After 上限？响应体上限？ | 读脚本 + 跑其单测；缺测就构造一个                      |
| 错误可操作性 | 错误是否泄漏内部细节？是否给 requestId？用户能否据此自救（缩小范围、重新登录、联系维护者）             | 逐条错误码对照设计 §6.4                                |
| 平台语义假设 | "D1 batch 即事务""SQLite 聚合对空集返回 X" 等假设是否被实验验证过                                      | 写最小实验（例：`json_group_array` 空集实测返回 `[]`） |

## B. 可维护性

- **复用顺序**（`AGENTS.md §2`）：仓库已有 → 框架内置/官方集成 → 成熟第三方 → 最小自定义。发现重复实现、平行契约（前端/文档/Skill 各写一份字段定义）即为缺陷。
- **分层边界**（可直接 grep 验证）：`src/web` 不得导入 `src/worker`；`src/shared` 不得依赖 DOM、D1 binding、`node:*`；服务端不得把内部表结构泄漏给前端。
- **规模信号**（观察阈值，不是硬规则，超出需能说出理由）：单文件 > 600 行、单函数 > 200 行、单组件同时承担数据获取+校验+渲染+上传。
- **死代码与残留**：未使用导出、恒真常量（`const ready = true`）、注释掉的旧路径、过期 TODO。
- **命名与语言**：代码英文、UI 文案中文；同一概念在不同层是否换了名字（导致契约漂移）。
- **测试与实现耦合**：测试是否复刻实现细节（改实现必改测试却证明不了行为）？是否只在测试辅助函数里做断言，真实入口没覆盖？
- **依赖卫生**：版本是否固定、许可是否可接受、体积是否合理、维护状态、新增依赖是否说明了"已有库为何不能覆盖"。
- **文档同步**：设计变更记录/版本号、OpenAPI、Skill 数据字典、README 的命令与数字是否与代码一致（数字必须实测）。
- **可诊断性**：失败时是否只有一句"服务暂时不可用"而无法定位；日志是否记录了 requestId/路由模板/状态码而不含个人数据。

## C. 测试覆盖空洞（专项）

按下面的模式逐条扫，命中即写入"永久测试建议"（不要自己补进 `tests/`）：

1. **测试辅助函数掩盖协议差异**：`request()`/`api()` 之类包装是否无条件补齐 `Content-Type`/`Origin`/`If-Match`，而真实客户端不会。
2. **只测 happy path**：写路径是否有失败与回滚断言；错误码是否有正例与反例。
3. **mock 冒充验收**：stub fetch、JSDOM、静态 CSS 断言、本地 mock 认证被当成真实浏览器/Access/真机验证。
4. **断言被削弱**：`toEqual` 退化成 `toBeTruthy`、只断言状态码不断言数据、断言前先 `if` 掉分支。
5. **边界未覆盖**：空集、全 NULL、上限±1（10000 明细、150000 行、20 MiB、300 组、50 条目、366 天）、年份 1900/9999、DST 两侧。
6. **新增分支未测**：本轮改动引入的错误分支、并发分支、迁移分支。
7. **验收项无证据**：对照 `docs/design.md §12.2` 的 A01–A21，逐条标"已覆盖 / 部分覆盖 / 未覆盖"，未覆盖的写进报告的"验收覆盖真空"。

## D. 报告里的表述纪律

- 静态推导只能是 `L2`，必须写明"未运行"；不要把"看起来会"写成"会"。
- 工具行为不确定时先做最小实验，用实验输出替代推测。
- 已知被文档承认的缺口只标"仍存在"，不重复上报（见 `known-gaps.md`）。
- 可维护性条目要给"改哪里、为什么值得改、改完如何验证"，避免只给审美意见。
